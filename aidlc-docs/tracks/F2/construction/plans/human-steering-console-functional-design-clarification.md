## 배경: Q8에서 합의된 동작 (제가 이해한 설계)

- 사람이 어떤 종목을 손대면(`/buy`,`/sell`,`/flatten`) 그 종목은 **"사람-락(human-lock)"** 상태가 된다.
- 이후 **에이전트가 그 종목에 대해 내리는 진입/청산 결정**은 자동 실행되지 않고 **사람 승인 대기**로 보류된다.
  콘솔이 이를 띄우고, 사람이 승인/거부한다. 승인 → RiskManager→Broker로 실행. 거부 → 실행 안 함.
- **승인/거부 결과는 에이전트에게 다시 전달**되어(저널/프롬프트), 에이전트가 "왜 안 됐는지" 알고 무한 재시도하지 않게 한다.
- **예외(승인 불필요):** 보호주문 — 미보호 포지션에 OCO/스탑 **등록**, 기존 OCO **수정**은 에이전트가 자율로 한다
  (불변식: 모든 포지션은 보호되어야 함). 이건 게이트에 걸리지 않는다.

아래는 이 설계의 미정 지점들입니다.

### CQ1 — 사람-락 종목에 대해 "승인 대기"로 걸리는 에이전트 동작 범위는?
A) **신규 매수(BUY)만** — 사람이 청산한 종목을 에이전트가 다시 사려는 경우만 승인 대기. 그 외(추가 매도 등)는 자동.
B) **모든 재량 거래(BUY·SELL)** — 사람-락 종목에 대한 에이전트의 매수/매도 모두 승인 대기. (단, 보호주문은 항상 예외) (권장)
C) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: B. 다만, 한번 허용하면 락이 풀림. 다시 사람에 의해 락이 걸릴 수 있음. 락 시스템 필요.

### CQ2 — 승인 대기 건을 콘솔에서 어떻게 띄우고 처리할까? (UX)
평범한 stdin REPL에서는 사람이 입력 중일 때 갑자기 끼어드는 프롬프트가 깨지기 쉽습니다.
A) **알림 줄 + 명령형 처리 (권장)** — 대기 발생 시 한 줄 알림 출력
   (예: `⚠ 승인 대기 #3: 에이전트 BUY AAPL $5000 — /approve 3 또는 /reject 3`), `/pending` 으로 목록 확인,
   `/approve <id>` / `/reject <id>` 로 결정(거부 시 사유 선택 입력 `/reject 3 <사유>`).
B) **블로킹 인터랙티브** — 대기 발생 시 콘솔이 즉시 y/n 프롬프트로 전환(다른 입력 일시 차단). 단순하지만 입력 흐름이 끊김.
C) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: A.

### CQ3 — 사람-락의 지속 기간과 해제 방법은?
A) **당일 유지 + 수동 해제 (권장)** — 락은 그날 세션 동안 유지, 다음 거래일에 자동 해제,
   필요하면 `/unlock <SYM>` 으로 즉시 해제(이후 그 종목 에이전트 거래는 다시 자동).
B) **영구 유지** — 사람이 `/unlock <SYM>` 하기 전까지 계속(거래일 넘어가도 유지).
C) **일회성** — 다음 에이전트 결정 1건만 승인 받고, 처리되면 락 자동 해제.
X) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: A. 당일 유지지만 에이전트가 락 해제 유발하는 거래 할지 그 결정 승인시 락 해제, 거부시 락 유지. 이후 에이전트가 또 요청 가능하나, 두번 거부 시 해당 날짜 영구 거부.

### CQ4 — 파괴적/lifecycle 명령 정의 확정 (Q5 후속)
아래 정의로 확정할까요?
- `/flatten <SYM>` = 해당 종목 100% 시장가 청산(동일 RiskManager 게이트) + 그 종목 resting 보호주문 취소. `[y/N]` 확인.
- `/flatten all` = **전 종목** 청산 + **모든** resting 주문 취소. **강한 확인** 필요.
- `/kill` = `/flatten all` + `/pause`(신규 리서치/진입 중단). **강한 확인** 필요.
- `/halt-entries` / `/allow-entries` = 신규 BUY만 차단/허용(기존 포지션 관리·청산·보호는 유지). `[y/N]`.

A) 위 정의 그대로 확정. (권장)
B) 위에서 일부 수정 필요(아래에 어느 명령을 어떻게 바꿀지 적어주세요).
X) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: A 그대로.

### CQ4-b — "강한 확인"의 형태는? (`/flatten all`, `/kill`)

B) 영향 요약 + y/N — 예: `5개 포지션·8개 주문 취소 예정 [y/N]` (재입력 없이 한 번 더 확인).

### CQ5 — 실행/런치 모델 확정 (Q3 후속)
Q1=B(인-프로세스 REPL)라 콘솔은 곧 데몬입니다. 따라서:
A) **monitor.sh가 데몬+콘솔을 한 패널로 띄운다 (권장)** — `scripts/monitor.sh`에 패널을 하나 추가/지정해
   거기서 `main.py --mode agent`(REPL 포함)를 실행하고, 나머지 패널은 지금처럼 파일을 tail. 이 패널이
   입력하는 콘솔이 됨. tmux라 항상 TTY + detach/attach 가능. (이 경우 데몬은 monitor.sh로 시작하게 됨.)
B) **데몬은 따로 실행, monitor.sh는 모니터만** — 그러면 인-프로세스 REPL의 입력 패널이 monitor 안에 없게 됨
   (별도 터미널의 데몬 콘솔에 직접 입력). 분리 운영엔 맞지만 모니터와 입력이 한 화면에 안 모임.
X) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: A.

### CQ6 — 테스트용 페이퍼 계정 (Q10 질문에 대한 답 + 확인)
**제 권장:** 자동 테스트(파서/확인/직렬화/lifecycle/reconcile 로직)는 기존 `SimulatedBroker`로 계정 없이 커버됩니다.
하지만 **실 Alpaca 페이퍼 대상 수동 스모크 테스트**는, 지금 돌고 있는 라이브 에이전트와 **같은 페이퍼 계정+같은 workspace**를
쓰면 충돌합니다(두 데몬이 decisions.jsonl/cursor/positions 공유 → 꼬임; `/kill`·`/flatten all` 테스트가 라이브 실험 포지션을 날림).
→ **별도 Alpaca 페이퍼 계정(별도 API 키) + 별도 workspace 디렉터리**를 권장합니다(worktree와 합쳐 완전 격리).

A) **별도 페이퍼 계정 + 별도 workspace로 격리 (권장)** — 가장 안전. (Alpaca 대시보드에서 페이퍼 계정 추가 가능.)
B) **계정은 그대로, workspace만 분리** — 단, 수동 스모크 동안 라이브 데몬을 잠시 멈추고 진행(라이브 실험 일시 중단).
C) **자동 테스트(SimulatedBroker)만으로 충분** — 실 페이퍼 수동 스모크는 생략.
X) 기타 (아래 [Answer]: 태그 뒤에 설명)

[Answer]: A로 하겠음. 이미 페이퍼 계정은 만들었음. 추후 테스팅시 격리된 testing workspace를 주의깊게 만들어야 함.
